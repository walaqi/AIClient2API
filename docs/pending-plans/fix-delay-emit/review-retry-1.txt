P0 — 必须修复
================================================================================

[P0-1] 重试递归路径下 keep-alive 启动逻辑被跳过, 导致重试期间 524 仍会复发
--------------------------------------------------------------------------------
原计划"位置 1"将 keep-alive 启动放在 `handleUnifiedResponse` 的
`if (!isRetry)` 块之后, 文字描述说 "把 keep-alive 启动放在 isRetry 检查
之外, 每次进入 handleStreamRequest 都重启新 timer", 但 diff 给出的具体
位置是在 `if (!isRetry) { await handleUnifiedResponse(res, '', true); }`
之后紧接着的位置 — 这点本身没问题, 不在 `if (!isRetry)` 块内, OK。

但还需明确两件事, 否则实施时容易出错:

1) catch 块内递归切凭证 (common.js:856 / 926) 时, 子调用进入新栈帧,
   因 `currentRetry > 0` ⇒ `isRetry = true`, 跳过 `handleUnifiedResponse`,
   但**仍会执行后面的 setInterval 启动代码**。这正是期望行为。
   计划应明确写出"keep-alive 启动代码必须在 `if (!isRetry)` 块**之外**",
   现在的 diff 里这段代码紧跟在 if 块之后但没用大括号包住, 仍在函数体
   顶层 — 实施者若误把它挪进 `if (!isRetry) { ... }` 块, 重试期间没有
   keep-alive, 524 会再次出现。

2) 父调用的 timer 必须在递归发生**之前**关停。当前 catch 路径:
       catch -> stopKeepalive() -> ... -> 递归 handleStreamRequest()
   ✅ 计划"位置 3"已在 catch 入口立即 stopKeepalive, 这是对的。
   但 429 同账号重试分支 (common.js:843-861) 在 catch 里, stopKeepalive
   已先执行, 没问题。

**修改要求**: 在"位置 1"diff 上方加一行注释, 强调 setInterval 块**不**
得放进 `if (!isRetry)` 内, 并补一句单元测试断言:
   "递归调用 (currentRetry > 0) 应能观测到 keep-alive 注释行写入"。


[P0-2] `clientDisconnected` 在 isRetry 时被覆盖逻辑让 stopKeepalive 关闭语义错位
--------------------------------------------------------------------------------
看 [common.js:619-623](src/utils/common.js#L619-L623):
   let clientDisconnected = retryContext?.clientDisconnected || { value: false };
   if (!isRetry) {
       clientDisconnected = { value: false };
   }

注意逻辑反直觉: !isRetry 时**重置**为新对象, isRetry 时**沿用**父级的对象引用。
这意味着重试栈帧里的 onClientClose / onClientError 监听器都不会被注册
(common.js:637 `if (!isRetry) res.on(...)`). 父级的监听器仍持有父级的
stopKeepalive 闭包引用 — 当客户端在重试期间断开, 父级 onClientClose
触发, 会调 **父级的** stopKeepalive(), 而当前活动的是**子级 timer**,
父级 stopKeepalive 对子级的 keepaliveTimer 无效, 子级 timer 继续 tick。

子级 timer 的回调里检查的是子级的闭包变量 `clientDisconnected.value`
(对象引用从父级传下来), 父级 onClientClose 把 `clientDisconnected.value`
置 true 后, 子级 timer 下次 tick 会自检通过 clearInterval 自停 —
**所以最坏情况延迟 25s 才停, 不会 leak**, 但这条隔代关停链应在计划里
写清楚, 避免实施 / 后续维护时被误改。

**修改要求**: 风险点中补一条:
   "递归重试期间 client 断开 → 父级 onClientClose 不直接关停子级 timer,
   依赖子级 timer 的 clientDisconnected.value 自检在下次 tick (≤25s) 关停。
   由于回调内只写注释行且 res 已 destroyed, 写失败被 try/catch 兜住,
   无副作用。"


[P0-3] `CONFIG?.STREAM_KEEPALIVE_INTERVAL_MS` 取值——CONFIG 在递归路径中可能为 undefined
--------------------------------------------------------------------------------
common.js:616 `const CONFIG = retryContext?.CONFIG;` — 首次进入函数时
retryContext 为 null, CONFIG = undefined。计划"位置 1"放在
`if (!isRetry)` 块**之后**, 此时 CONFIG 仍可能 undefined (取决于调用方:
common.js:1516 给 retryContext 传了 CONFIG, OK; 但若有其他调用入口或
未来扩展未传, 就会拿不到配置)。

`Number(CONFIG?.STREAM_KEEPALIVE_INTERVAL_MS) || 25000` 的 ?. 已经处理
了 undefined; **Number(undefined) = NaN, NaN || 25000 = 25000** ✅ 安全。

但计划文档 "配置项" 一节写的是 "用户可在 configs/config.json 顶层覆盖",
没写"必须通过 retryContext 传递到 handleStreamRequest"。实施者若直接
import 全局 CONFIG, 会破坏现有的依赖注入风格。

**修改要求**: "配置项"一节明确说明: 配置读取**仅通过 retryContext.CONFIG**,
不要新引 import。或者 fallback 直接写常量 25000 + 注释"如需配置化, 通过
retryContext 注入"。

P1 — 建议修复
================================================================================

[P1-1] keep-alive timer 与 try 块的相对位置
--------------------------------------------------------------------------------
当前计划: setInterval 创建在 try 块**外** (位置 1), stopKeepalive 函数
也在 try 块外定义。这意味着如果 setInterval 创建之后、try 进入之前
有任何同步异常 (理论上极小概率), timer 不会被清理。

更稳妥的做法: 把 stopKeepalive 函数定义放外面, setInterval 创建放进
try 块第一行。或者用 try / finally 包整个流程, 在 finally 里
stopKeepalive — 现有 finally 块 (common.js:959) 已存在, **直接在
finally 块开头加一行 stopKeepalive() 是最干净的**, 可以替代位置 3、4
的多处插入, 也覆盖位置 5 的双保险。

**建议**: 用 finally 兜底替代位置 3、4 的多处 stopKeepalive 插入, 保留
位置 2 (首次写 event/data 前) + finally 兜底两处即可:
- 位置 2: 立即停止避免无意义的注释行混在真实数据流前 (用户体验)
- finally: 一切异常路径的最终兜底 (正确性)

这样改动从 5 处压到 2 处, 维护风险更小, 也不需要担心 catch 内多个
return 路径是否都覆盖到 stopKeepalive。

[P1-2] keep-alive 回调里检查列表冗余
--------------------------------------------------------------------------------
计划里的检查: `keepaliveStopped || anyDataSent || clientDisconnected.value
|| res.writableEnded || res.destroyed`

- `anyDataSent` 检查是冗余的: 一旦写过真实 data, 已通过位置 2 的
  stopKeepalive() 主动停掉; 即使遗漏, 写一行 `: keepalive`不影响协议。
  保留也无害, 但语义有点混 — anyDataSent 本意是"能否切凭证重试", 不是
  "keep-alive 是否该停"。

- `clientDisconnected.value` 与 `res.writableEnded` 与 `res.destroyed`
  通常同时翻 true。`event-broadcast.js:54` 只检查了 `writableEnded` 和
  `destroyed`, 这两项基本足够。

**建议**: 简化为 `keepaliveStopped || res.writableEnded || res.destroyed`,
注释里说明: clientDisconnected.value 翻 true 时 res 也已 destroyed, 不需
重复检查。简化的好处: keep-alive 回调和 event-broadcast.js 现有实现
保持一致, 降低认知负担。

[P1-3] 注释行内容设计——`: keepalive ${Date.now()}\n\n`
--------------------------------------------------------------------------------
event-broadcast.js 现有实现是 `:\n\n` (零字节有效负载, 6 字节)。
计划改用 `: keepalive ${timestamp}\n\n` (~30 字节)。

写入时间戳的好处: 抓包 / 日志排查时能看出注释是哪个时刻发的。
坏处: 多 24 字节, 但 25s 一次, 一天 ~3.4KB, 完全可忽略。

**建议**: 保留时间戳, 但去掉 `keepalive` 字面量改用更短的 `: ka ${ms}\n\n`
或保持原样均可, 这是细节问题, 不阻塞。

[P1-4] 客户端误解析 keep-alive 注释——计划里点名了 4 个客户端但没列证据
--------------------------------------------------------------------------------
风险点 5 说 "Claude Code (`@anthropic-ai/sdk`), OpenAI Node SDK (`openai`),
curl (`-N`), 浏览器 EventSource — 都正确忽略"。这是事实, SSE 规范明确,
但更彻底的做法: 在验证方案 1 (Caddy / nginx mock 方案) 里同时跑这 4 个
客户端, 收集真实输出, 作为发布前 checklist。

**建议**: 验证方案 1 末尾加一条: "用 Claude Code CLI 实际请求一次, 看
SSE 流首尾是否完整, 有无解析报错"。

[P1-5] 25s 默认间隔——是否应区分 Cloudflare/Cloudfront/AWS ALB
--------------------------------------------------------------------------------
默认 25s 对应 Cloudflare 100s 是充裕的 (~4 次心跳)。但常见反代默认值:
- AWS ALB idle_timeout 默认 60s → 25s 仅 2 次, 边缘情况下可能擦边
- Nginx proxy_read_timeout 默认 60s → 同上
- Cloudfront 60s → 同上

25s 在大多数场景是安全的, 但若用户用 ALB 且把 idle_timeout 调到 30s,
就有可能擦边。

**建议**: 配置项 doc 里写明: "若中间代理超时 < 50s, 应将该值调至代理
超时的 1/3 ~ 1/2"。或者把默认值降到 15-20s, 给极端用户更多余量。我
个人倾向降到 20s, 多发几个字节换取更高的鲁棒性。

[P1-6] 验证方案 2 (jest 单测) 已知阻塞——应给出降级路径
--------------------------------------------------------------------------------
计划自己说 "jest/babel 配置上一轮报过 import.meta.url 问题, 若此处复现
仍走手动测试路径, 不强求自动化覆盖"。这态度合理, 但应把"手动测试"
具体化:

**建议**: 方案 2 改为: 写一个独立 .mjs 脚本 (不依赖 jest), 内部
mock res, 直接 import handleStreamRequest, 跑 3 个场景, 用断言 + 日志
打印替代 expect(). 这样不依赖测试框架配置, 仍可自动化。脚本放
scripts/test-keepalive.mjs, 放 npm script 入口。

[P2-1] 是否值得把 keep-alive 提取成独立函数
--------------------------------------------------------------------------------

建议压到 2 处调用, 完全没必要抽函数, 内联读起来更直接。
**建议**: 不抽, 保持内联。

[P2-2] event-broadcast.js 的 keep-alive 复用问题
--------------------------------------------------------------------------------
计划说 "复用其结构", 但 event-broadcast.js 是 UI 监控用的全局事件流,
和 LLM SSE 完全不是同一种场景, 状态变量和清理时机也不同。**真正复用
的只是 setInterval + res.write(':\n\n') 这一行模式**, 没必要做代码层
共享。计划自己也只用作"参考", 这点处理是对的。

[P2-3] 是否在写完 SSE 头后立刻写第一个 keep-alive 而不是等 25s
--------------------------------------------------------------------------------
当前: handleUnifiedResponse → 25s 后才第一次 keep-alive。
极端情况: 客户端到本服务的 TCP 连接, 本服务到上游的 axios 请求, 在前 25s
没有任何字节流过 (HTTP/1.1 头算 socket 第一次 write, 算字节, OK; 但
如果代理只看 body 字节呢?)。

Cloudflare 524 计时器从"上游不再返回字节"开始, HTTP 头算字节, 所以 25s
内首字节只要在 95s 内到, 安全。但如果上游冷启动 > 25s + 95s = 120s,
keep-alive 第一次 tick 才发生在 25s, 中间已浪费 25s, 不过仍在 100s 阈
值内, OK。

**讨论**: 不必为此提早第一次 keep-alive。25s 内 axios 已经发出请求,
TCP 上有 SYN/握手字节; 中间代理监控的是应用层字节, HTTP 头算应用层
字节。25s 已写过响应头给客户端方向 (handleUnifiedResponse), 客户端到
本服务这段链路没问题。本服务到上游这段, axios 自己持有 socket, 与
keep-alive 无关。

确认: 默认 25s 不需要提前。

【对原计划风险点的补充】

[新风险 R8] 反向代理本身会 buffer SSE 注释行?
--------------------------------------------------------------------------------
若中间代理开启了 response buffering (Nginx 默认 proxy_buffering on),
注释行可能被代理攒到 buffer 满才一起转发, 反而触发上游超时检测时
看不到字节。

事实: Cloudflare 对 text/event-stream 自动禁用 buffering (响应头有
Content-Type: text/event-stream 即触发); Nginx 需用户手动设置
`proxy_buffering off` 或 `X-Accel-Buffering: no` 头。

**建议**: handleUnifiedResponse 里 SSE 头追加 `X-Accel-Buffering: no`,
作为 keep-alive 的兜底保险。这是一行代码:
   res.writeHead(200, { ..., "X-Accel-Buffering": "no" });

不在原计划范围内, 但与本次修复目标强相关, 可一起做。

[新风险 R9] STREAM_KEEPALIVE_INTERVAL_MS 验证缺失
--------------------------------------------------------------------------------
计划说 "设为 0 / 负数 / 非数字 → 走默认 25s; 不提供完全禁用 keep-alive,
因为现网证据表明它是必需的"。

但若用户配置了 1ms (恶意 / 误配), 会每秒写 1000 次注释行, CPU/带宽
被吃光。

**建议**: 加最小值钳位:
   const interval = Math.max(5000, Number(CONFIG?.STREAM_KEEPALIVE_INTERVAL_MS) || 25000);

低于 5s 的间隔无意义, 直接用 5s 兜底。
