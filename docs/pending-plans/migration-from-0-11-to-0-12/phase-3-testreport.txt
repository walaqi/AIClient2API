[F3] §3.6 上游 prompt cache 在 SOCIAL/Builder-ID 端点不主动 engage
  现状: §3.6 stream 子用例两次请求 metering credits 几乎一致
        (0.03117 / 0.03218), 上游 message_start 报告的 inputTokens
        在两次请求间也几乎一致 (1447 / 1444). 由 calculateCacheTokens
        反算得到 cacheReadTokens=0 / cacheCreationTokens≈1447.
  控制实验: 临时移除 claude-kiro.js:2023 timestamp 注入再跑两次,
        cache_read 仍 = 0, credits 数值落在抖动范围内. 即 timestamp
        注入不是 cache miss 的成因.
  对比: §3.6 非流式子用例报出 cacheReadTokens > 0
        (1329 / 1288), 但其分母 inputTokens=2862 是 countTextTokens
        本地估算值 — 与 stream 路径取自 message_start 的 1447 不同;
        同 credit 总额下, 较大的 inputTokens 分母让反算公式
            creation = (inputCost - inputTokens * cacheReadPrice)
                       / (cacheCreatePrice - cacheReadPrice)
        给出更小的 cacheCreationTokens, 余下被记入 cacheReadTokens.
        这部分是 calculateCacheTokens 简化假设 (model-pricing.js:144-160
        已用注释点明) 的反算工件, 不能作为上游真实命中的证据.
  推测根因 (未独立验证, 不在本期范围):
    - SOCIAL/Builder-ID 端点 (CodeWhisperer/SendMessage) 在当前 codepath
      上未把 Anthropic prompt cache 流量 engage. 客户端侧 conversationId
      稳定 / cachePoint 标记 / system prompt byte 稳定三件事都到位
      (§3.1, §3.5, §2.5 均 PASS), 已用尽客户端可控范围.
    - IDC 账号 / 切到 amazonq endpoint 是否表现不同, 未在本期测试.
  影响范围: 仅影响 §3.6 "上游真实 cache 命中" 的端到端可观测性. Fix-F
        plumbing 本身正确, response.usage 字段已可填充, 计费下游若需要
        cache_read_input_tokens 数值仍能拿到 (理解为反算估值).
  建议: 单独 issue 跟进上游 cache engagement, 含
        (a) IDC 账号侧对照测; (b) calculateCacheTokens 在 inputTokens
        来源不同时的口径统一 (考虑非流式也用 message_start 报告值,
        若上游非流式响应里有同等字段). 不阻塞 Phase 3 sign-off.
