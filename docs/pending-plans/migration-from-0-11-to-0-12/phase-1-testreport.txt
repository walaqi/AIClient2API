实质性 bug 修复 (Phase 1 期间排查并落地, 已保留在工作区)
==========================================================================

[Fix-A] 字节通道修复 (§1.1 主阻塞)
  根因: axios 不设 responseType='arraybuffer' 时默认按 text 解码,
        二进制 event-stream 帧里的高字节 (0x80+) 被替换为 U+FFFD,
        再次 toString('utf8') 时 U+FFFD 重新编码为 3 字节 ef bf bd,
        每个原 1 字节高字节膨胀 3 倍, 12 字节 prelude/totalLen 字段被打乱,
        awsParseEventStreamFrames 只能解出 1 个帧 (其余靠 break 静默吞掉).
  修复:
    - claude-kiro.js:2489-2495  axios responseType: 'arraybuffer'
    - claude-kiro.js:2868-2879  _processApiResponse 把 raw Buffer 透传给 parseEventStreamChunk;
                                文本视图仅用于 ASCII bracket-tool 扫描
    - claude-kiro.js:2597       400 错误体走 _getErrorResponseText 处理 Buffer
  对照来源: Kiro-account-manager 用 undici ReadableStream<Uint8Array> 直读字节.

[Fix-B] dispatcher unwrap (Kiro 0.12 包装事件兼容)
  根因: Kiro 0.12 把 event payload 改成包装形态:
        {assistantResponseEvent:{content:"..."}} / {toolUseEvent:{...}} / {reasoningContentEvent:{text:"..."}}
        emitEventFromParsed 的启发式分发只看 flat 形态, 包装层未拆.
  修复:
    - aws-event-stream-parser.js:71  emitEventFromParsed 入口加 unwrap:
        parsed = parsed.assistantResponseEvent || parsed.toolUseEvent
                 || parsed.reasoningContentEvent || parsed;
  TODO 保留: 长期应改用 :event-type header 派发, 而非 payload shape 启发式.

[Fix-C] 非流式 thinking pipeline 缺口
  根因: Kiro 0.11 时代思考链以内联 <thinking>...</thinking> 文本嵌在 content 中;
        0.12 改为独立 reasoningContentEvent 帧.
        非流式聚合循环 (claude-kiro.js:2287-2320) 旧实现对 reasoning 事件 "静默丢弃",
        在 0.12 下导致服务端正确返回的思考链被客户端整体丢失,
        响应缺 content[].type='thinking' 块.
  修复:
    - parseEventStreamChunk 返回 shape 扩展为 {content, toolCalls, thinking}
    - 聚合循环 event.type === 'reasoning' 分支累加 thinking += event.data
    - _parseEventStreamChunkLegacy 同步返回 thinking: '' 占位
    - _processApiResponse 透传 thinking
    - generateContent 在 thinkingRequested 路径直接构造
        [{type:'thinking', thinking}, {type:'text', text}]
        不再依赖 _toClaudeContentBlocksFromKiroText (0.12 服务端不再内联标签).
  对照: 流式路径 claude-kiro.js:3560-3574 已正确处理 reasoning → thinking, 未动.

[Fix-D] thinking 字段 Kiro 0.12 enum 兼容 (§3.2 就地落地, 见说明)
  根因: Kiro 0.12 服务端 additionalModelRequestFields.thinking.type
        enum 只接受 ["adaptive", "disabled"], 不再接受 "enabled".
  修复:
    - claude-kiro.js:2206-2218  enabled 一并归到 adaptive, 下发 {type: 'adaptive'};
                                disabled / 未识别: 不下发该字段.
  说明: 计划原文写 "Phase 1 路线 A 临时改, 跑完回滚, §3.2 单独立 PR".
        实际上整个 Phase 3 代码本身就还未 commit, 不存在路线 A 是临时叠加的边界,
        因此与用户讨论后决定保留这条映射作为 §3.2 正式落地, 注释从 "临时改法 / 待回滚"
        改写为 "Kiro 0.12 服务端 enum 只接受 ..., enabled 一并归到 adaptive".

  现状: claude-kiro.js:1401 用 isIdc (账号属性) 决定 CLI/IDE user-agent,
        与 endpoint.origin 解耦. SOCIAL 账号即使被路由到 AmazonQCLI 端点,
        发出的仍是 KiroIDE user-agent.
  观察: §1.5 测试中, SOCIAL+AmazonQCLI 服务端返回 400, payload 形态客户端侧
        已确认正确 (origin: CLI, 无 agentContinuationId/agentTaskType).
        合理推测服务端对 user-agent 与 origin 字段的搭配做了一致性校验,
        SOCIAL+IDE-UA+CLI-origin 是不被接受的组合.
  待对齐: user-agent 应该跟 endpoint.origin 走还是跟账号 isIdc 走?
        计划文档 §1.3 描述偏模糊, 需要先与上游对齐再决定是否调整 1401 处.
  影响范围: 仅在 KIRO_PREFERRED_ENDPOINT='amazonq-cli' 时触发, 默认路径不受影响.
